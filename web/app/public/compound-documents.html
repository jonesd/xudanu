1. The Core Concept

A compound document is a document whose content is assembled from live pieces of other documents — not copies. When a source document changes, every compound document that references it automatically reflects the change.

This is Ted Nelson's original vision for transclusion: the same content can appear in multiple places simultaneously, always in sync, without duplication.

┌─────────────────┐ ┌──────────────────────────┐ │ Source Work A │ │ Compound Document │ │ │ │ │ │ "The quick brown│─────►│ [span: Work A, 0:15] ──► │ "The quick brown" │ fox jumps over │ │ │ │ the lazy dog" │ │ (literal text) │ " and then " │ │ │ │ └─────────────────┘ │ [span: Work B, 4:20] ──► │ "rendipity happens" ┌─────────────────┐ │ │ │ Source Work B │─────►└──────────────────────────┘ │ "Seseapprendipit│ ↑ resolved text shown to reader │ y happens" │ └─────────────────┘ The compound doc doesn't store "The quick brown" — it stores a reference (Work A, chars 0-15). When Work A changes, the compound doc automatically reflects the new text.
A compound document assembles content from multiple sources via live references

2. The Three Stores (and why it's confusing)

Every work in xudanu has up to three separate data stores that can hold text content. Understanding how they interact is the key to understanding the system:

Store What it is Type Where
O-Tree / CRDT The work's primary text buffer. What you edit in the editor. Persisted as revisions. Static Copy Edition entries in the ordered tree
Compound Edition A side-table of elements (text literals + live span references). Optional metadata. Live References compound_editions: HashMap<BeId, CompoundEdition>
Transclusion Links Inter-document hyperlinks with attribution and provenance chains. Metadata links: HashMap<BeId, HyperLink>
Why it's confusing
When you place a transclusion, all three stores get written simultaneously. The O-tree gets a text copy, the compound edition gets a span reference, and the link system gets an attribution record. They can drift apart if you edit one without the others.

3. Mechanism 1: The O-Tree (your text)

This is the primary content store. When you type in the editor, you're modifying the O-tree. It's a CRDT — conflict-free, supports concurrent editing, and persists as numbered revisions.

// Simplified structure
Edition {
    orgl_root: OrglRoot,      // the ordered tree (o-tree)
    endorsements: [...],      // who has vouched for this
    // entries: [(position, RangeElement)] — text characters at positions
}

// What you see in the editor IS the O-tree text
editor.textContent === otree.get_text()

STATIC COPY — When text from another work is pasted into the O-tree, it becomes a copy. It does not update when the source changes. This is just like copying text in a normal editor.

4. Mechanism 2: Compound Editions (live spans)

This is the transclusion engine. A compound edition is an ordered list of elements, each either literal text or a live span reference:

CompoundEdition {
    elements: [
        Text { content: "Introduction. " },
        Span  { span: CompoundSpan {
            source_work_id: 1006,   // which work to reference
            char_start: 0,          // character offset in source
            char_end: 46,           // end offset (exclusive)
        }},
        Text { content: " Conclusion." },
    ]
}

LIVE REFERENCE — The span doesn't store text. It stores a pointer (work_id, char_start, char_end). When you resolve the compound, the system fetches the current text from each source work and assembles the result:

Compound Edition: ┌──────────────┐ ┌──────────────────┐ ┌──────────────┐ │ Text: "Intro"│ │ Span: W1006 [0:5]│ │ Text: " End."│ └──────┬───────┘ └────────┬─────────┘ └──────┬───────┘ │ │ │ │ ┌────────▼─────────┐ │ │ │ Fetch from W1006 │ │ │ │ "Hello World!!!" │ │ │ │ chars [0:5] │ │ │ │ = "Hello" │ │ │ └────────┬─────────┘ │ │ │ │ ▼ ▼ ▼ Resolved text: "Intro" + "Hello" + " End." = "IntroHello End."
Resolution: the compound engine fetches live text from each source and concatenates

What happens when a source changes?

The compound engine has span migration — when Work A is edited, all compound spans referencing Work A have their offsets automatically adjusted:

BEFORE: Source Work A = "Hello World" Compound span: [0:5] → resolves to "Hello" EDIT: Insert "GPS " at position 0 → "GPS Hello World" AFTER: Span migrated by +4 chars Compound span: [4:9] → resolves to "Hello" ✓ The compound document still shows "Hello" — the reference followed the text.
Span migration: offsets shift to track content through edits

5. Mechanism 3: Transclusion Links (attribution)

Links are the provenance and attribution layer. They record why a piece of text appeared in your document, who put it there, and the chain of derivation:

HyperLink {
    link_id: 0x1A2B,
    origin: this_work,          // where the link lives
    destination: source_work,   // where the content came from
    origin_ref: HyperRef {      // the span in THIS work
        start_position: 42,
        end_position: 88,
        excerpt: "The quick brown fox",
    },
    link_types: [3, 7],         // typed links (quotation, paraphrase, etc.)
}

Links power the backfollow engine — the system that detects when content from one work appears in another, using BLAKE3 content fingerprints. This is separate from compound spans: links track attribution, compound spans track live content resolution.

Key distinction

Compound spans answer: "What text should I show here?"
Links answer: "Where did this text come from and who vouches for it?"

A transclusion creates both, but they serve different purposes and can exist independently.

6. The Current Flow (step by step)

Here's exactly what happens today when you place a transclusion:

1
Select text in a source work
You open Work A (a source document), highlight some text, and the selection gets "held" by the transclusion hook (holdSelection()). The excerpt text and its character offsets are stashed.
2
Navigate to your compound work
You switch to Work B (the document you're composing). A floating TransclusionBadge appears showing the held excerpt.
3
Place the transclusion
handlePlaceTransclusion() fires and does three things at once: 
// 1. Insert excerpt text into O-tree (STATIC COPY)
setText(text.slice(0, pos) + excerpt + text.slice(pos));

// 2. Record compound span (LIVE REFERENCE)
compound.addSpan(text, pos, excerpt, sourceWorkId, charStart, charEnd);

// 3. Create attribution link (METADATA)
transclusion.placeTransclusion(sourceWorkId, excerpt, charStart, charEnd);
4
Three stores are now written
The O-tree has the text copy, the compound edition has the span reference, and the link system has the attribution record. All three describe the same content, but through different mechanisms.
5
Reading mode shows resolved text
When you switch to reading mode, displayText switches from the O-tree text to compound.resolvedText — the live-resolved version that fetches current content from sources.
The drift problem
If you later edit the O-tree text directly (delete the transclusion paragraph, add text around it), the O-tree text and the compound edition diverge. The compound panel lets you fix the compound edition, but the O-tree copy becomes stale. This is the core UX confusion.

7. The Design Tension

There are two possible architectures, and we're currently straddling both:

ARCHITECTURE A: "Compound as side-table" (CURRENT) ┌────────────────────────────────────────────────┐ │ Work B │ │ ┌─────────────────┐ ┌──────────────────────┐ │ │ │ O-Tree (primary)│ │ Compound Edition │ │ │ │ "Intro Hello End"│ │ [Text, Span, Text] │ │ │ │ (editable copy) │ │ (live references) │ │ │ └────────┬────────┘ └──────────┬───────────┘ │ │ │ │ │ │ editing mode reading mode │ │ shows this shows resolved │ └────────────────────────────────────────────────┘ Problem: two copies of content, can drift apart ARCHITECTURE B: "Compound as primary" (FUTURE?) ┌────────────────────────────────────────────────┐ │ Work B (compound type) │ │ ┌────────────────────────────────────────────┐ │ │ │ Compound Edition = THE document │ │ │ │ [Text, Span→A, Text, Span→B, Span→C, Text] │ │ │ │ │ │ │ │ Resolved text is the ONLY text │ │ │ │ No O-tree copy needed │ │ │ └────────────────────────────────────────────┘ │ └────────────────────────────────────────────────┘ No drift possible — there's only one source of truth
Two possible architectures: side-table (current) vs. primary (proposed)

Architecture B would eliminate the drift problem entirely, but requires a new work type whose primary content IS the compound edition. The O-tree would only be used for non-compound works.

9. Use Cases: Simple to Visionary

Level 1 Quotation Anthology

A document that collects excerpts from multiple source works. Each excerpt is a live span — if the source is corrected or updated, the anthology reflects it.

CompoundEdition {
    Text { "Notable quotes:\n\n" },
    Span { src: Shakespeare, [120:145] },  // "To be or not to be..."
    Text { "\n\n— Hamlet\n\n" },
    Span { src: Tolstoy, [3000:3080] },    // "All happy families..."
    Text { "\n\n— Anna Karenina" },
}
Level 1 Shared Boilerplate / Templates

Maintain a single "disclaimer" or "about" work. Every document that needs the boilerplate references it via a compound span. Update the source once, all documents update.

Level 2 Collaborative Study Guide

A study guide that assembles passages from a textbook (source work) with interleaved commentary (literal text). When the textbook is revised, the relevant passages in the study guide update automatically.

Text { "Chapter 3 discusses recursion. Key passage:\n\n" },
Span { src: Textbook, [4500:4600] },     // textbook passage
Text { "\n\nAnalysis: The author's approach to..." },
Span { src: Textbook, [4800:4900] },     // another passage
Text { "\n\nThis connects to..." }
Level 2 Multilingual Parallel Text

A document showing original text and translation side by side. The original language work and translation work are both sources. Edits to either propagate to the parallel reading view.

Level 3 Golden Thread / Deep Transclusion Chains

A compound document references another compound document, which references another, creating a chain of live transclusions. Resolution follows the chain recursively (up to 32 levels). This is Nelson's "golden thread" — following content back through layers of derivation.

Doc C (compound) → spans in Doc B (compound) → spans in Doc A (source)

Resolving Doc C recursively:
  1. Fetch Doc B's compound edition
  2. For each span in Doc B, resolve it against Doc A
  3. Assemble the final text from the entire chain
Level 3 Versioned Anthology with Reordering

An anthology where the editor can reorder, add, and remove excerpts without affecting the source works. Using the incremental compound ops (insert, remove, move), the editor restructures the composition while all spans remain live.

Vision Nelson's Original Vision: The Xanadu Docuverse

In the full vision, everything is transclusion. No document copies content — every document is a compound of live references to a universal docuverse. Authors are paid micropayments when their content is transcluded. Copyright becomes attribution tracking rather than access control.

xudanu implements the technical foundation: content-addressed storage, live span references, recursive resolution, and per-element provenance. The economic and social layers are future work.
