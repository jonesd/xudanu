What “xanalogical” means

“Xanalogical” is Ted Nelson’s word for the general class of document systems his Project Xanadu exemplifies — the way “hypertext” names the general class the web exemplifies. Lowercase and adjectival: a xanalogical system. “Xanadu” itself stays a proper noun for Nelson’s specific project (Project Xanadu, Xanadu 92.1, the trademark held by its owner).

Nelson, describing where the design settled: “The Xanadu design has essentially resolved to one basic document concept: parallel pages with visible connections.” (hyperland.com)

Those two visible properties are the whole of it:

  • Parallel documents — you read things side by side, origin beside quotation, original beside comment, version beside version. Nothing replaces anything; comparison is the native act.
  • Visible connections — the links between passages are first-class, shown where they connect, and they point both ways. You can see what connects to what you are reading, and follow it back.

Everything else in this page — the addressing, the versioning, the transclusions, the rights model — exists to make those two properties work without breaking.

Versus the web. The web shipped with one-way links that break when their target moves, no version management, and copy-paste as the reuse mechanism — the quotation detaches from its origin and the origin never knows. A xanalogical system inverts each choice: two-way unbreakable connections, permanent versions, and reuse by reference so the connection to the source survives. This is not nostalgia; it is a different set of guarantees. Where those guarantees matter — citation, comparison, provenance, concurrent editing — the xanalogical design remains the reference point.

The core ideas, in learning order

Each idea in two sentences, with the deep-dive documentation behind the link. The order matters: each idea fixes a problem the previous one creates.

1. Transclusion

The same content, appearing in two places, with one origin. Nothing is copied — the second appearance is the first, by reference — so when the source changes, every appearance reflects it, and the connection back to the origin is permanent and visible.

→ The transclusion engine, documented · transclusion architecture

2. Two-way, unbreakable links

A link is a first-class object connecting two specific passages — not a one-way jump but a visible, typed, bidirectional connection. Both ends always know about each other, so backlinks are native, and the link cannot dangle: the passages it connects are stable addresses, not disposable locations.

→ Links and backlinks · the Gold link model

3. Deep addressing — tumblers

Every character range of every version of every document has a permanent address. Gold’s form was the tumbler — a hierarchical address that never renumbers, so a reference written in 1988 still resolves today, to the character.

→ The document space and its algebra

4. Permanent versions

Editing does not overwrite; it creates new states of a document whose old states remain addressable. Combined with tumblers, this is why links never break: the thing they point at is still there, still named, still findable.

→ Editions and works — the content model

5. Rights at quote granularity

If reuse is by reference, then rights can attach to the act of reuse — quotation-level licensing, automatic attribution, and (in the original design) micropayment paths. Nelson’s name for this is transcopyright: permission to quote, granted once, settled at the level of the actual quotation.

→ The Gold model’s concept tables cover the original design; modern implementations choose their own licensing surface.

6. Transpointing windows — the reading interface

All of the above is machinery; this is what the reader sees: documents in parallel panes, connections drawn between the passages they connect, the connector lines adhering to characters as text moves. The interface is not decoration — parallel pages with visible connections is the design.

→ A running classic reader (one implementation’s door)

Where it came from — a short history

1960–65. Ted Nelson, a Harvard graduate student, begins designing a worldwide publishing system for the interactive screen — and coins the word hypertext (published 1965). His design diverges immediately from what would later ship as the web: visible two-way connection, parallel documents, reuse by reference.

1974. Computer Lib / Dream Machines publishes the vision to the generation that built personal computing.

1979. The Swarthmore summer: Roger Gregory and Mark S. Miller invent tumblers — the transfinite-number addressing scheme that lets any range of any version of any document be named, quoted and linked. The hard problem of deep addressing gets its answer before the decade ends.

1988–92. Autodesk buys a controlling interest; the funded team builds two systems — Green (Xu88) and the later Gold — implementing the full model in Smalltalk with a C++ translation.

1999. The code is released open source (MIT/X11) as Udanax. The release’s shape became its own story: the readable Smalltalk stayed largely internal while machine-generated C++ shipped — Don Hopkins’s famous review called it “uncommented glue gluing glue to glue.” The model was freed; the readability was not.

2014–. The after-lineage: Nelson’s own browser demos (OpenXanadu 2014 still runs; the 2016 xuCamb/perma.pub server did not survive), Green modern builds, addressing layers, ports reported but unreleased, and new independent systems in the same problem space.

One running implementation: Xudanu

Among the active systems, one is documented on this site — introduced here because a running system makes every idea above inspectable rather than historical.

Xudanu is an independent, open-source (Apache 2.0) implementation of the Gold document model in Rust and TypeScript, built by David Jones, whose earlier udanax-gold2java project translated the released Gold sources into Java (2003–2014). Xudanu is not affiliated with, endorsed by, or sponsored by Ted Nelson, Project Xanadu, the Xanadu Operating Company, or the Udanax team; it implements concepts from the open-sourced Udanax-Gold codebase using original code.

What carries over from Gold — the core algorithms, reused

  • Tumblers as typed hierarchical addresses, with Gold’s never-renumber allocation (the Sequence algebra) — the 1979 Swarthmore answer to deep addressing, implemented as specified
  • Enfilades — Gold’s tree structure for content and ranges — with crums now carried as BLAKE3 Merkle hashes, so subtree equality is checked by hash
  • Typed bidirectional links between passages, both ends visible, migrating through edits
  • Inline transclusions in the document tree itself — one source of truth, no side tables — whose spans migrate when sources are edited
  • The parallel reading interface — a classic reader presenting works side by side with their connections visible

What is new — modern technologies the Gold era did not have

  • Real-time concurrent editing via a purpose-built CRDT (the O-tree) — many authors editing the same work at once, converging without locks; the collaborative layer Gold never had
  • Cross-server reach — works addressable across servers by domain-anchored tumblers, public content fetched over HTTPS and verified by content hash
  • Cryptographic provenance — authorship spans signed and verifiable, an attribution log, per-work licensing options including transcopyright-style terms
  • A web-native reading and editing surface — browser app, WebSocket wire protocol, and agent-facing (MCP) tooling for the same operations

It runs as a public sandbox at demo.transclusion.org — open, no login needed to read. Source: github.com/jonesd/xudanu. The Gold model itself, mapped concept by concept, is documented at gold-heritage.html — that documentation describes the model, not any one implementation of it.

Reading paths by arrival

Just curious

Start with the story — Whatever happened to Project Xanadu? — then see who is building now in the census, then see the model itself in the Gold concept tables. Total: an evening.

Designer

The reading interface is the design. The classic reader (screenshots and live sandbox), then the document space — how positions, regions and displacements make parallel pages computable.

Builder

You want to build one of these. Start from the behaviors an engine must have: the test registry — the entry point of a build order through a working engine, a worked path for building a xanalogical engine in any language. Then the 17 rules as the spec in force, then the concept tables for the model, then the complexity comparisons to know which parts are hard.

Skeptic

Fair — the strongest critique is Gwern’s essay, and it deserves reading in full. Then weigh it against what actually runs: the census (what shipped, verified), the both-directions complexity pages (what is genuinely hard, conceded), and a live system where the connections do not break. The honest version of the debate needs both sides read.
