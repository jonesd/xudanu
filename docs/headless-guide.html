Running the server as a pure API backend — no browser, no frontend, just the document store, link engine, and CRDT collaboration over WebSocket and HTTP.

1. What Headless Means

Xudanu's server binary (xudanu-server) is a complete document store, link engine, and CRDT collaboration backend. The web frontend is optional — it's served as static files when you provide --static-dir, but the API is always available.

Headless = run the server without serving any UI. You interact with it entirely through the WebSocket protocol, HTTP endpoints, or the bundled CLI client. This is the architecture for:

  • API backends for custom frontends (mobile apps, desktop clients, other web apps)
  • Content pipelines (automated import, export, archiving)
  • Federation nodes (peer servers that relay content, not browsers)
  • CI/CD testing (integration tests use this mode)
  • Embedded systems (the wasm feature targets browsers)
No separate build exists or is needed. The same xudanu-server binary IS the headless server. Simply omit --static-dir and the frontend is not served.

2. Quick Start: Server + CLI

Start a headless server
# Start the server (API only, no UI)
xudanu-server run 127.0.0.1:8080 ./data

# Or with the demo corpus (optional)
xudanu-server run 127.0.0.1:8080 ./data --edit-policy public-sandbox --seed-links-demo

# Health check
curl http://127.0.0.1:8080/health
Connect with the CLI
# Interactive REPL mode
xudanu-cli ws://127.0.0.1:8080/xudanu repl

# Or one-shot commands
xudanu-cli ws://127.0.0.1:8080/xudanu create-work "My Document" "Hello, world"
xudanu-cli ws://127.0.0.1:8080/xudanu list-works
xudanu-cli ws://127.0.0.1:8080/xudanu create-link 1004 1005 3

3. The CLI Client

The xudanu-cli binary ships with every release. It connects over WebSocket and speaks the same protocol as the web frontend:

Link types: 1=Comment, 2=Reference, 3=Disagreement, 4=Quotation, 5=See Also. The full multi-ended link model (end-sets, gathered passages, links-to-links) is available via the WebSocket protocol directly — the CLI covers the common two-ended cases.

4. The WebSocket API

The full protocol lives at ws://<addr>/xudanu. Two formats are supported:

  • JSON — human-readable, good for development (?format=json)
  • Binary (postcard) — compact, good for production (?format=binary)
Example: create a work over JSON WebSocket
{"v": 2, "type": "request", "id": 1, "op": "session_connect"}
{"v": 2, "type": "request", "id": 2, "op": "session_login_public"}
{"v": 2, "type": "request", "id": 3, "op": "work_create",
 "payload": {"edition": {"text": "Hello, headless world"}}}

The full operation set (200+ operations) covers works, links, revisions, transclusion, annotations, trails, CRDT editing, federation, and more. See the wire protocol documentation generated by scripts/gen-wire-doc.py.

5. The HTTP API

Limited HTTP endpoints are available for simple integrations:

EndpointMethodDescription
/healthGETServer health and stats
/api/public/work/{id}GETPublic work content (published works only)
/csrf-tokenGETCSRF token for state-changing HTTP operations
/auth/*GET/POSTOAuth2 callbacks (GitHub, Google)
Most operations require WebSocket. The HTTP API is intentionally minimal — it exists for health checks, public content reads, and OAuth callbacks. All state-changing operations go through the WebSocket protocol.

6. Use Cases

Custom frontend (mobile app, desktop client)

Connect via WebSocket, speak the same protocol as the web frontend. The wasm build of the Xudanu library can be embedded in browser-based clients for offline-capable editing.

Content pipeline

Automated content import
#!/bin/bash
# Create a work from a file
CONTENT=$(cat article.txt)
xudanu-cli ws://server:8080/xudanu create-work "Imported Article" "$CONTENT"

# Link it to a topic work
xudanu-cli ws://server:8080/xudanu create-link $NEW_WORK_ID $TOPIC_ID 2

Testing and CI

Start a headless server in CI, run assertions against the WebSocket API, then stop it. The integration test suite (315 tests) already does this.

Federation node

A headless server with --peer flags joins the federation mesh and relays content between servers without serving browsers.

8. Federation Headless

Start a headless federation node
xudanu-server run 0.0.0.0:8080 ./data \
  --peer ws://peer1:8080/xudanu \
  --peer ws://peer2:8080/xudanu \
  --enable-cluster

Federation nodes replicate content across servers. A headless federation node is a relay: it stores and forwards content between peers without serving any browser clients. See FR-41 for the full mesh protocol.
