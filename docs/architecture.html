3. The Backend Module Map

The backend is organized into five layers (with two horizontal pairs at the same level), each depending only on the layer below it:

Six layers. Each layer depends only on the layer(s) below it. The server core orchestrates; the edition model holds the data.

The Gold heritage lives in the edition and entity layers. The enfilade (orgl.rs), canopy, hoist (widdershin), props (permissions algebra), DagWood (versioning), and tumbler addressing are all faithful ports from the original Udanax-Gold C++ codebase. The transport, persistence, and crypto layers are entirely modern Rust.

4. The Enfilade: How Documents Live in Memory

Every Edition is backed by an orgl — an immutable (copy-on-write) tree of Loaves. Each node in the tree carries three cached aggregates, maintained by construction through every edit:

The enfilade: an immutable Loaf tree. Edits rebuild only the O(log n) path from root to leaf. Unchanged subtrees are Arc-shared across editions at zero cost.

The three per-node crums

CrumTypeMaintainedPurpose
crum[u8; 32] (BLAKE3)By construction (every tree op)O(1) content equality (FR-34 fast path)
OwnerSetSorted owner-club setBy construction (A-3)License/permission descent queries
char_lenusizeBy construction (A-3 P2)Char-space extent for subtree pruning
Copy-on-write is the design decision that makes everything work. No shared node is ever mutated. Every edit rebuilds its path through constructors that compute all three crums by construction. This means there is never a staleness window — Gold needed the widdershin patching protocol for its mutable tree; our immutability subsumes it (A-3 P4 closed by design).

5. The Link Model

A link is a sentence with blanks: the type is the verb, and each end fills one blank. A gathered end fills one blank jointly with multiple passages.

The link model: a sentence with blanks. The link canopy provides enfiladic query matching (subtree pruning by work-range and type bits).

This is not the web’s link model. Web links are one-way, one-ended, break when content moves, and carry no type. Xudanu’s links are bidirectional (both ends know about each other), multi-ended (any number of ends, each a set of passages), typed (Disagreement, Quotation, Comment…), unbreakable (span migration follows edits), and can target other links (connections about connections). No mainstream system has this expressiveness.

Headless deployment

The server is the product — the frontend is optional. Without --static-dir, the binary serves only the API:

WebSocketws://<addr>/xudanuFull protocol: works, links, CRDT editing, subscriptions

The xudanu-cli binary ships with the release and provides create, revise, link, list, query, and revision-history operations over the same WebSocket protocol as the frontend — no browser needed.

6. The Fulltrace: The Version DAG

Every work gets a TracePosition = (branch, position) at creation. Clubs get their own branches; works owned by a club allocate on that branch. The result is a hierarchical namespace queryable via the partial order.

The fulltrace: works get TracePositions on club branches. "Works under club A" is a subtree visibility query.

7. Data Flow: From Keystroke to Disk

The edit pipeline: keystroke → WebSocket → CRDT merge → enfilade update (O(log n)) → WAL → chunks → root chunk manifest. Live updates flow back to subscribers immediately.
