1. The Problem: Why the O-Tree Is Slow

Xudanu's live editing engine is the O-tree CRDT — a purpose-built collaborative editor that operates on the enfilade (the Gold-inherited Loaf tree). It works. It carries the full content model. But under heavy concurrent editing, it hits a structural ceiling.

The O-tree's cost under concurrency vs the lattice. The structural difference: reconciliation vs append.

The FR-50 audit found the pattern: every measured performance defect lived at the seam between the CRDT layer and the Gold-inherited document model — span migration over char offsets, edition materialization per op, fingerprint reconciliation. The patches worked, but the pattern said the seam itself was the recurring cost.

2. The Thesis: Write-Once Is Convergent by Construction

The lattice's core insight: if storage is write-once and content-addressed, convergence is automatic. No merge algorithm can garble because there's nothing to reconcile:

  • Concurrent writers mint new dots (immutable units with unique IDs)
  • Nobody overwrites — old units become tombstones (still immutable)
  • Replicas sync by exchanging crum diffs — O(changes), already implemented in FR-34
  • The view (what the user sees) is a projection: live dots minus tombstones

Two concurrent inserts: the lattice appends dots (no merge); the O-tree reconciles copies (three-way merge).

3. What the Lattice Is

Concretely, the lattice is a weight-balanced binary search tree keyed by Sequence positions — the same tumbler-derived addressing that Gold used. Each node is either a live unit (a dot with content and an author) or a tombstone (a marked deletion).

Key properties

  • Write-once: units are immutable; deletion = tombstone (also immutable)
  • Content-addressed: every subtree carries a BLAKE3 crum
  • Concurrent-safe: no overwrites, no merge algorithm, convergence by construction
  • Sequence-native: positions are tumblers, not char offsets — the Gold addressing model
  • O(log n) operations: insert, delete, lookup — the tree is weight-balanced
  • O(changes) sync: replicas exchange crum diffs, not full state

4. The Shadow: What Runs Today

The lattice is running inside the production server as a dual-write shadow (FR-51 Phase 4):

The dual-write shadow: every edit goes to both engines; the shadow asserts text equality after every delta.

What the shadow has already accomplished: it caught the F6 duplication bug (the O-tree was silently duplicating ~100 chars under interleaving) and the F10 compounding bug (per-op cost doubling). Both were fixed because the shadow was the oracle — the lattice was right, the O-tree was wrong. This is why the FR-51 doc says "divergence may be the shadow being right."

How to enable it

Run the server with the shadow
xudanu-server run   --lattice-shadow

# Then enroll works (admin op via WebSocket):
# 0x0353: LatticeShadowEnroll { work_id }
# 0x0354: LatticeShadowStatus (telemetry: enrolled/ops/matches)
# 0x0355: LatticeShadowClear { work_id } (rollback)

5. The Gap: What the O-Tree Has That the Lattice Doesn't

The lattice is a text-editing engine. The O-tree is a document system. This is the entire gap:

Concurrent merge✓ three-way✓ dot-based—
Provenance (Ed25519 signatures)✓✗C-1
Transclusion (inline shared content)✓✗C-2
Span migration (links follow edits)✓✗C-3
Annotations (char ranges)✓✗C-3
Structural elements (blobs, sets, paths)✓✗C-2
Crums/OwnerSet (canopy queries)✓✗C-4
Federation (anti-entropy replication)✓PartialC-4
The 300-700× speed gap is real but not urgent. The O-tree's compounding is FIXED (F10) — it runs flat at ~50ms/op. The gap only matters under heavy interleaving on large documents. If that's not your current bottleneck, the cutover isn't urgent.

6. The Cutover: The Six-Phase Plan

The full plan is in docs/dev/FR-51-cutover-plan.md. Summary:

The six phases. C-0 is the precondition; C-2 is the hard part; C-5 is the switch. Total ~6-8 weeks.

Not scheduled. The cutover is a roadmap for when the timing is right. The shadow serves as the correctness oracle and the performance target today. When a concrete need for the lattice's speed emerges (heavy collaborative editing, federation at scale, or the CrossSpace2 compound documents that want a lattice substrate), the plan is ready.

When should you start?

When one of these becomes a real need:

  • Heavy collaborative editing — multiple concurrent editors on large documents where 50ms/op is felt
  • Federation at scale — the lattice's O(changes) sync is the right substrate for multi-server replication
  • CrossSpace2 compound documents — FR-40 A-4 wants the lattice as its position space
  • When the O-tree's remaining issues (placement divergence, migration cost) become blocking

Until then, the shadow runs, the plan is documented, and the path is clear.
