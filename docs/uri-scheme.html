The xudanu:// URI Scheme

Version 1.0 · 5 November 2026 · specification for the provisional IANA registration

A xudanu: URI identifies a work, a revision of a work, or a character span within one, in a Xudanu docuverse. Because positions are tumblers — addresses, not offsets — a span reference survives edits elsewhere in the document, and because every read returns a BLAKE3 content hash, every citation is verifiable after the fact.

xudanu://work/42                     the current edition of work 42
xudanu://work/42?rev=3              revision 3 of work 42 (pinned, immutable)
xudanu://work/42#span=10,150        characters 10–150 of the current edition
xudanu://work/42?rev=3#span=10,150  the same span in the pinned revision

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described in RFC 2119. This version describes exactly what the reference implementation emits and accepts today; forms under design are named in Future forms and deliberately given no grammar.

1. What a xudanu URI identifies

A work is a document in a docuverse: an evolving sequence of editions, each a snapshot of its full content. A xudanu URI therefore identifies one of three things:

FormIdentifiesStability
xudanu://work/42The current edition of work 42 at dereference timeTime-dependent: the target moves as the work is revised
xudanu://work/42?rev=3Revision 3 of work 42Immutable: a pinned edition
…#span=10,150Characters 10–150 of the identified editionSpan-stable: survives edits before character 10 or after 150

This one scheme covers both halves of citation that other systems split across two: the unpinned form is a living pointer (“what it says now”), the ?rev= form is a permanent pin (“exactly what it said then”).

2. Syntax

The grammar uses the ABNF notation of RFC 5234; DIGIT is defined there.

xudanu-URI = "xudanu://work/" 1*DIGIT [ rev ] [ span ]

rev        = "?rev=" 1*DIGIT
span       = "#span=" 1*DIGIT "," 1*DIGIT

Additional constraints, expressed here and normative:

  • In span, the first integer MUST be strictly less than the second. A zero-length or reversed span is invalid.
  • All integers MUST be representable as unsigned 64-bit values.
  • When both are present, rev precedes span. There is exactly one query component and one fragment component; additional query parameters or fragment content make the URI invalid.

3. Component semantics

ComponentMeaning
xudanuThe scheme name. Registered provisionally with IANA; see section 9. Emitters MUST produce it in lowercase.
workA fixed type discriminator occupying the authority position. It is not a hostname and MUST be the literal string work. See section 4.
path digitsThe server-local numeric identifier of the work, assigned by the docuverse server at creation. Emitters MUST NOT produce leading zeros.
?rev=If absent, the URI identifies the current edition — a time-dependent address. If present, it identifies exactly one revision: revisions are immutable once created, so the URI is a permanent pin. Revision numbers are assigned by the server; nothing guarantees they are contiguous or that any particular number exists.
#span=A character range in the identified edition, half-open [start, end): the first integer is the first character included, the second is one past the last. Coordinates are positions in the tumbler coordinate system — addresses, not byte offsets — so a span continues to identify the same passage when text elsewhere in the work changes.

4. Naming authority and scope

The authority slot of a v1 xudanu URI holds the literal string work, which names a type, not a host. The actual naming authority is the docuverse session in which the URI is interpreted: work identifiers are assigned by a server, and the same identifier may name unrelated works on two different servers.

A v1 xudanu URI is therefore context-local, like a relative reference in HTTP: it is meaningful between parties that already share a session with the same docuverse server. This is the form every tool emits today, for the good reason that it is the form every tool can resolve. Two further forms — naming the origin server, and naming content directly by hash — are under design; see Future forms. Until specified, a consumer MUST NOT infer server or content addresses from a v1 URI.

5. Canonical form and tolerated input

Emitters MUST produce the canonical form:

  • lowercase scheme and literal work; plain decimal integers without leading zeros, signs, or whitespace
  • query before fragment; no other components

The reference implementation's parser additionally tolerates surrounding whitespace (the input is trimmed) and leading zeros (xudanu://work/007 identifies work 7). It rejects everything else outside the grammar: a missing identifier, a non-decimal or signed integer (?rev=abc, ?rev=, /+7), a reversed or zero-length span, unknown query parameters, and any fragment not matching span=s,e. Malformed components are rejected, never repaired: an implementation MUST NOT silently drop a rev it cannot parse.

Reference implementation. WorkRef::parse and WorkRef::to_uri in src/server/mcp.rs, with round-trip and rejection tests in the same file. This specification documents that grammar; if the two ever disagree, the tests fail.

6. Comparison

Two xudanu URIs identify the same resource if and only if their canonical forms are identical: same work identifier, same rev (present or absent), same span (present or absent). Leading zeros and surrounding whitespace are not significant.

One deliberate asymmetry: xudanu://work/42 and xudanu://work/42?rev=3 are different URIs even when revision 3 is currently the latest edition — the first is a pointer that will follow future revisions, the second is a pin that never will. For citations that must not drift, consumers SHOULD use the pinned form.

7. Dereferencing and verification

Dereferencing happens through the tools of the session the URI is used in: read and search tools accept these URIs, resolve transclusions live, and return span content together with its BLAKE3 fingerprint. A verify tool exists for the citation discipline: given a URI and quoted text, it confirms the quote against the docuverse.

Constructing or parsing a xudanu URI performs no network or filesystem I/O — URIs are inert addresses. All authority checks happen at dereference time on the server (see section 8).

Consumers who need durable citations SHOULD record and compare the BLAKE3 fingerprint returned at read time. Content hashes are what make a pinned reference checkable years later: trust the hash, not the citation.

8. Security considerations

  • URIs are inert. Parsing triggers no network action. A URI embedded in a document does not cause fetches, tracking, or callbacks; the dereferencing party always acts explicitly.
  • A URI grants no authority. Dereferencing remains subject to the server's permission model. Passing a URI to a party without read access to the work does not give them access.
  • No injection surface in the grammar. Every component is decimal digits with a fixed delimiter set; there is no escaping, no percent-decoding of semantic content, and no way to smuggle additional query or fragment parameters past a conformant parser.
  • Verify cited content. A URI proves nothing about bytes. The BLAKE3 fingerprint returned by read operations is the verification mechanism; consumers relying on quoted content SHOULD compare fingerprints rather than trust the quote.

10. Future forms

This version defines only the context-local form, because it is the only form tools emit today. Two further authority forms are planned, each of which corresponds to an operation that already exists in the shipped wire protocol. They will be specified — grammar and semantics — in a future revision of this document at this URL; the registered scheme name does not change when it does.

Planned formNamesShipped operation it will map to
Origin-server formWhich server owns the work — provenance, permissions, the current-edition pointerCrossServerFetchWork (wire op 0x0f06)
Content-hash formThe content itself, wherever it is held: any server holding the bytes can serve it, and the hash is the verificationFederatedTransclusionQuery (0x1701), FederatedContentFetch (0x1702)

Both planned forms keep v1 addresses valid and unambiguous by construction: the authority literal work is reserved for the context-local form, permanently. An origin-server URI will carry the server's name in the authority position with its path beginning /work/ — a consumer distinguishes the two from the authority slot alone, and no v1 URI can ever be reinterpreted as naming a server.

Until a form appears in a published revision of this document, implementations MUST NOT extend the grammar by inference. The content-hash form is the deeper of the two — location-independent addressing over BLAKE3 content — and is the direction of the federated docuverse: works are named locally, content is found by hash anywhere it lives.
