1. Clubs — Identity and Permission Units

In Udanax-Gold, a Club is the fundamental identity unit. Every user, group, and permission set is a Club. Clubs own works, control access, and sign content. There is no separate "user" concept — everything is a Club.

Club structure

FieldTypePurpose

Club types

Personal Club

One per user. Has credentials (password or public key). Owns the user's works and edits. Has an encrypted Ed25519 signing key for attribution.

Group Club

A named collection of member clubs. Used for team permissions: "editors", "reviewers", "public". Members inherit the group's access rights.

Public Club

Special club for anonymous/guest access. Users who haven't signed in operate under the public club. Their edits are attributed to "anonymous".

Signature Club

Internal club that holds signing keys. Every personal club has a signature club that owns its Ed25519 keypair.

Udanax-Gold origin: Clubs are directly from the original C++ codebase. Gold had a Club class with recursive membership (clubs containing clubs). Xudanu currently implements flat membership (no nesting) but retains the sponsorship concept for work vouching.

2. Credentials

A club can have one of two credential types:

Password

Credential::Password { phc_hash }

Stored as a PHC-format Argon2id hash. The PHC string encodes the algorithm, parameters, salt, and hash, making it self-describing and future-proof.

Public Key

Credential::PublicKey { verifying_key }

A 32-byte Ed25519 verifying key. The client proves identity by signing a challenge with the corresponding private key.

3. The Lock Hierarchy

Locks control access to clubs. A club may have a lock that must be opened before the club's authority can be used. The lock system implements the Strategy pattern via the Lock trait:

4. KeyMaster — Authority Tracking

The KeyMaster tracks which clubs a session has proven identity for. When a lock is opened, the resulting KeyMaster contains the set of authorized club IDs.

Authority operations

  • KeyMaster::make(club_id) — create authority for a single club
  • KeyMaster::merge(other) — combine authority from multiple authentications
  • KeyMaster::has_authority(club_id) — check if the session can act as this club
  • KeyMaster::clubs() — iterate all authorized clubs
Udanax-Gold origin: The original C++ KeyMaster had incorporate() (merge authority) and removeLogins() (revoke). Xudanu implements make() and merge() but not revocation yet.

5. Provenance & Attribution

Every piece of content has a cryptographic provenance chain. The system tracks:

  • ElementProvenance — author public key, display name, club ID, timestamp, and author type (Human/LLM/Historical) for individual elements
  • SpanProvenance — Ed25519-signed proof covering a contiguous range of characters, linking them to their author

Signing and verification

  • sign_element(signing_key, element, author_identity) — creates ElementProvenance
  • sign_span(signing_key, text, author_identity, region) — creates SpanProvenance with a signature over the text + region
  • verify_span_provenance(provenance) — verifies the Ed25519 signature, returns true if valid

Attribution log

The server maintains an AttributionLog (src/server/transport/attribution_log.rs) that records every authorship change. The log:

  • Writes to attribution.log in the data directory
  • Supports verification: verify_log() checks every entry's cryptographic integrity
  • Is append-only: entries are never modified or deleted
  • Is checked by preflight_check() on server startup

6. Session Lifecycle

  1. Connect: WebSocket connection established. A Session is created with a unique SessionId.
  2. Authenticate: Client sends credentials. Server opens the club's lock, producing a KeyMaster.
  3. Author identity: The session is assigned an OtreeAuthorIdentity (public key, display name, club ID) for CRDT attribution.
  4. Operate: All subsequent operations (read, edit, star, trail) are performed under the session's authority.
  5. Disconnect: Session is cleaned up. Awareness state is removed. Active edits are preserved (auto-saved via CRDT).

7. Security Monitor

The SecurityMonitor (src/server/transport/audit.rs) tracks threat levels per session and IP address:

  • Auth failures — repeated wrong passwords
  • Protocol violations — malformed messages, invalid operation codes
  • Permission denials — attempts to access unauthorized resources
  • Grab conflicts — concurrent edit conflicts

Threat levels escalate: None → Low → Medium → High → Critical. At Critical, the session is recommended for disconnection. All events are written to a structured audit log.
