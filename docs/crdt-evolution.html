1. The Problem: Concurrent Document Editing

When two people edit the same document at the same time, their changes can conflict. The fundamental challenge is:

The fundamental concurrent editing problem: two users diverge from the same base.

Six families of solutions exist, each with different trade-offs:

2. Historical Context: How Gold Did It

Udanax-Gold (1998) solved concurrent access with pessimistic locking — the "work grabbing" model:

Gold's work grabbing model: pessimistic locking, one editor at a time.

Gold's approach was simple and correct: Only one user can edit a document at a time. No conflicts are possible because concurrent edits don't exist. The trade-off: no real-time collaboration.

4. Level 1: Three-Way Merge SHIPPED v0.9.2

How it works

The server maintains a per-session base edition for each client. When a client sends a text delta, the server:

  1. Applies the delta to the client's session base (not the current edition)
  2. Three-way merges: session base vs current edition vs delta-applied edition
  3. LastWriterWins (LWW) resolves conflicts — the incoming edit wins
  4. Updates the client's session base to the merged result
  5. Relays the delta to other connected clients

Level 1 three-way merge: non-overlapping edits are preserved. Same-region conflicts use LWW.

5. Level 2: Operational Transformation (OT)

Recommendation: Skip this level. OT adds significant complexity without the benefits of Level 3. Go directly to Level 3 (position-based CRDT).

OT works by transforming concurrent operations before applying them. If A inserts at position 5 and B deletes position 3, the server transforms A's insert to position 4 (accounting for B's deletion).

Pros

  • Both edits survive when in different regions
  • Full undo/redo across collaboration boundaries
  • Mature theory (OT research since 1989)
  • Production-proven (Google Docs since 2006)

Cons

  • Transform functions are complex (many edge cases)
  • Still server-authoritative (no offline, no P2P)
  • Transform correctness is hard to verify formally
  • Same-region conflicts still need LWW fallback
  • ~2-3 months effort for minimal gain over Level 1

6. Level 3: True Position-Based CRDT FR-8 PLANNED

The O-tree already has immutable positions — inherited from Gold's enfilade heritage. Each character gets a position at creation time that never changes. Level 3 exposes these positions in the wire protocol.

Position-based addressing: inserting between [0,0] and [0,1] creates [0,1,t] where t is a timestamp. Existing positions never change.

Why this matters for users

  • Never lose data: Every keystroke from every user is preserved. If A and B both edit the same word, both versions survive (interleaved or side-by-side)
  • Work offline: Edit on a train, sync when you reconnect. All changes merge cleanly
  • Faster collaboration: No merge computation needed — operations apply directly
  • Multi-server: Two xudanu servers can accept edits independently and converge

7. Level 4: Distributed CRDT with Federation

Level 4 extends Level 3 across multiple servers. Any server accepts edits, operations propagate via federation sync, all replicas converge.

Level 4: Multi-server editing. Users on different servers edit the same document, changes propagate and converge.

8. Alternative Approaches

Yjs / Yrs (CRDT library)

Mature CRDT library used by Notion, Figma, Atlassian. Would replace the O-tree entirely.

  • Battle-tested, production-proven at massive scale
  • Built-in awareness, undo/redo, offline support
  • Rich ecosystem (bindings for React, ProseMirror, etc.)
  • Abandons Gold's O-tree and enfilade heritage
  • Different data model (not compatible with edition/span provenance)
  • Would require rewriting transclusion, links, attribution

Automerge (JSON CRDT)

CRDT for JSON documents with offline-first design.

  • Excellent offline support
  • Works with any JSON structure
  • Heavy memory overhead
  • Not designed for text editing specifically
  • Would require adapting to text model

Diamond Types (byte-level CRDT)

Position-based CRDT operating at the byte level, used in Figma.

  • Extremely efficient (minimal metadata)
  • Production-proven at Figma scale
  • Proprietary implementation (not open source)
  • Byte-level — doesn't integrate with O-tree positions

Our approach: O-tree position CRDT (FR-8)

Use Gold's own O-tree positions, already in the codebase, as the CRDT position identifiers.

  • Preserves Gold heritage (enfilade positions)
  • Integrates naturally with transclusion, links, attribution
  • No external dependency
  • Full control over implementation
  • Requires implementing CRDT logic ourselves
  • ~4 months development effort

9. FR-8 Design Details

Wire Protocol

Delta operations reference O-tree positions instead of sequential character counts:

Current (v0.9.x):     Retain { count: 18 }, Insert { text: " world" }

FR-8:                Retain { positions: [[0,0], [0,1], ..., [0,17]] }
                     Insert { after: [0,17], text: " world", origin: "session-42" }

Positions are O-tree region coordinates. They are immutable — assigned at creation, never reassigned.

Tombstone Deletes

Deleted characters are marked, not removed. This preserves position stability for other clients that may still reference them.

struct OtreeEntry {
    position: XnPosition,       // immutable
    element: RangeElement,
    origin_session: SessionId,  // who created this
    is_tombstone: bool,        // deleted but not removed
    tombstone_after: Option<u64>, // revision when deleted
}

Tombstones are invisible in rendered text but present in the data model. Periodic compaction removes tombstones that no client references.

Vector Clocks (Causal Ordering)

Each operation carries a vector clock — a map of {session_id: operation_count}. This enables:

  • Detecting concurrent operations (neither happened-before the other)
  • Deterministic ordering (same operations in any order = same result)
  • Offline sync (operations queue and apply in causal order on reconnect)

Offline Editing

The client maintains a local operation queue (using IndexedDB). When offline:

  1. All edits are stored locally with their O-tree positions
  2. On reconnect, the client sends queued operations to the server
  3. The server applies them position-by-position (no merge needed)
  4. The server relays to other clients
  5. All replicas converge — guaranteed by CRDT properties

Federation Sync

Position-based operations are naturally distributable:

  1. Server A accepts edit from client
  2. Server A applies to its O-tree replica
  3. Server A relays to Server B via anti-entropy gossip
  4. Server B applies to its O-tree replica
  5. Both replicas converge

This enables true multi-server editing — the Xanadu docuverse vision where documents live across servers.

Compaction

Tombstones accumulate over time. Compaction removes them:

  • Trigger: When tombstone ratio exceeds 30% of total entries
  • Process: Create new edition without tombstones
  • Position remap: Build mapping from old positions to new
  • Client notification: Send crdt_compacted event with remap table
  • Safety: Only compact tombstones older than N revisions

11. Success Criteria

  • Two clients editing the same paragraph simultaneously — both edits preserved (no data loss)
  • Client disconnects, edits offline for 10 minutes, reconnects — edits sync without conflict
  • Two servers accept edits independently, sync converges to identical state
  • 10 concurrent users editing a 10K-word document — no data loss, sub-second latency
  • Mathematical convergence proof (all replicas eventually identical)

12. Convergence Guarantees

Theorem: Given any two replicas that have received the same set of operations (in any order), the rendered text is identical.

Proof sketch:

  • Insert operations are uniquely identified by (position, origin, timestamp)
  • Delete operations are idempotent (tombstone marking — marking twice has no effect)
  • Retain operations preserve order (positions define a total order)
  • Operations commute because positions are immutable and unique
  • Therefore: any permutation of the same operation set produces the same result
