How Chunks Work

Xudanu stores all data as content-addressed chunks. The chunk filename IS its BLAKE3 hash:

data/chunks/
  00/004fdcb3...3817c.xchunk    ← hash starts with "00"
  61/61c8d5b2...8746a.xchunk    ← hash starts with "61"
  ab/abcdef12...34567.xchunk

This means:

  • Verification is free: compute BLAKE3 of file contents, compare to filename. No separate hash database needed.
  • Deduplication is automatic: same content = same hash = same file. rsync skips it.
  • Corruption is detectable: if a file's content doesn't match its filename hash, it's corrupt.
  • Repair is simple: copy the correct file from backup. Same hash = same path.
What gets backed up: chunks (all works, editions, links, annotations, clubs), manifest.json (dual slots), WAL, key history, security logs, blobs, attribution data.

Backing Up Offsite

Single destination

# Local disk
./scripts/backup-offsite.sh data /mnt/backup/xudanu --verify

# Remote server via SSH
./scripts/backup-offsite.sh data user@remote:/backups/xudanu

Multiple destinations

# Backup to local + remote simultaneously
./scripts/backup-offsite.sh data /mnt/backup/xudanu user@remote:/backups/xudanu --verify

What the backup does

  1. Copies manifest and metadata (small, fast)
  2. Syncs chunks via rsync (incremental — only new/changed chunks transfer)
  3. Syncs blobs (if any)
  4. Syncs WAL and attribution data
  5. Writes .backup-info with timestamp and chunk count
  6. Verifies all chunks (with --verify)
Incremental: rsync only copies chunks that are new or changed. For a server with 10,000 chunks where 5 new chunks were added, only 5 files transfer.

Repairing Corrupt Chunks

If you suspect corruption (server reports deserialization errors, chunks fail to load):

# Scan all chunks, verify BLAKE3 hash, repair from backup
./scripts/restore-offsite.sh /mnt/backup/xudanu data repair

What repair does

  1. Scans every chunk file in data/chunks/
  2. Computes BLAKE3 hash of file contents
  3. Compares to filename (the expected hash)
  4. If mismatch: copies correct version from backup
  5. If file is empty/missing: copies from backup
  6. Reports: OK count, corrupt count, repaired count, unrepairable count
BLAKE3 verification requires: pip3 install blake3. Without it, only file-size checking is performed.

Example output

Verifying target chunks via BLAKE3 (hash = filename)...

  CORRUPT: 004fdcb3...3817c
    -> Repaired from backup
  Checked 500 / 549...

Repair summary:
  OK:           548
  Empty:        0
  Corrupt:      1
  Repaired:     1
  Unrepairable: 0

Full Restore

For disaster recovery — restore everything from backup to a fresh directory:

# Restore to a new data directory
./scripts/restore-offsite.sh /mnt/backup/xudanu /path/to/new-data full

# Or overwrite existing (requires confirmation)
./scripts/restore-offsite.sh /mnt/backup/xudanu data full

What full restore does

  1. Copies manifest.json and all manifest backups
  2. Copies key_history.json and server.key
  3. Copies security logs
  4. rsyncs all chunks from backup
  5. Copies blobs, WAL, and attribution
  6. Reports final chunk count
After restore: Run xudanu-server verify <data_dir> to confirm the server can read all data. The server performs its own integrity check on startup.

Merge Restore

Add only missing chunks from backup without touching existing data:

./scripts/restore-offsite.sh /mnt/backup/xudanu data merge

Useful when:

  • A few chunks were accidentally deleted
  • You want to add chunks from an older backup
  • The server is running and you don't want to stop it

Verification

Standalone verification (no backup needed):

# Check all chunks — verify BLAKE3, find empties, check manifest references
./scripts/verify-chunks.sh data

# Find and remove corrupt/empty chunks
./scripts/verify-chunks.sh data --fix

# Save report to file
./scripts/verify-chunks.sh data --report verification.txt

What verification checks

  1. Chunk integrity: BLAKE3 hash of each file vs filename
  2. Empty files: zero-byte chunks
  3. Manifest references: all chunks referenced by manifest exist on disk
  4. Orphaned chunks: chunks on disk not referenced by manifest
  5. Dual manifest slots: backup manifest files exist

Multiple Backup Locations

For redundancy, back up to multiple destinations:

# Daily: local NAS
./scripts/backup-offsite.sh data /nas/xudanu --verify

# Weekly: remote server
./scripts/backup-offsite.sh data user@offsite:/backups/xudanu --verify

# Monthly: cold storage (S3, Glacier, tape)
aws s3 sync data/chunks/ s3://my-bucket/xudanu/chunks/
aws s3 cp data/manifest.json s3://my-bucket/xudanu/manifest.json

For restore, try each location until the chunk is found:

# Try local backup first
./scripts/restore-offsite.sh /nas/xudanu data repair

# If still missing, try remote
./scripts/restore-offsite.sh user@offsite:/backups/xudanu data merge

Automation & Cron

Daily backup via cron

# crontab -e
0 2 * * * /path/to/scripts/backup-offsite.sh /path/to/data /mnt/backup/xudanu >> /var/log/xudanu-backup.log 2>&1

# Weekly remote backup
0 3 * * 0 /path/to/scripts/backup-offsite.sh /path/to/data user@remote:/backups/xudanu >> /var/log/xudanu-backup.log 2>&1

Weekly verification

0 4 * * 0 /path/to/scripts/verify-chunks.sh /path/to/data --report /var/log/xudanu-verify.log

Pre-backup checkpoint

For maximum consistency, trigger a checkpoint before backup:

# Force checkpoint via admin API, then backup
curl -s http://127.0.0.1:8080/health | grep -q '"status"' && \
    ./scripts/backup-offsite.sh data /mnt/backup/xudanu --verify

What Causes Corruption

CausePreventionRecovery
Disk failure (bad sectors)RAID, SMART monitoringRepair from backup
Power loss during writeUPS, WAL + dual manifestServer replays WAL on startup
Filesystem corruptionJournaling FS (ext4, ZFS)Verify + repair from backup
Accidental deletionPermissions, read-only mountMerge restore from backup
Memory corruption (bit flip)ECC RAMBLAKE3 detects mismatch
Ransomware / maliciousImmutable backup (WORM)Full restore from cold storage
Xudanu's built-in protections:
  • Dual manifest slots — crash during manifest write keeps the old one
  • WAL (Write-Ahead Log) — replayed on startup to restore in-memory state
  • BLAKE3 content addressing — corruption is always detectable
  • Orphaned chunk cleanup — GC removes unreferenced chunks
  • Server verify subcommand — full integrity scan
