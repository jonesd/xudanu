# FR-12: Admin Monitoring Dashboard

> A real-time monitoring and management screen for admin/staff to understand
> system health, detect anomalies, and diagnose issues.

## Goal

Provide a single-screen view of the Xudanu server's operational state, with
automatic anomaly detection and quick access to diagnostic information.

## What We Built (Phase 1)

`AdminDashboard.tsx` — a full-screen overlay accessible via a small "Admin"
button in the bottom-right corner. Polls `/health` every 5 seconds.

### Features
- **System metrics**: works, links, editions, clubs, blobs, sessions, operations
- **Health status badge**: green (ok) / red (degraded)
- **Anomaly alerts**: checkpoint stuck, high sessions, degraded status
- **Health checks**: automated pass/fail for key indicators
- **Server identity**: server ID, last checkpoint time, total operations
- **Quick links**: /health JSON, server info
- **Auto-refresh**: 5-second polling with timestamp

### Alert Conditions
| Alert | Trigger | Severity |
|---|---|---|
| Checkpoint stuck | `last_checkpoint_ago_secs > 300` | Warning |
| Degraded status | `status != "ok"` | Critical |
| High sessions | `sessions > 40` | Warning |

## Future Phases

### Phase 2: Enhanced monitoring
- **Session list**: show active sessions with IP, work, duration
- **Security event log**: recent audit events from chained security log
- **Rate limiter status**: blocked IPs, notification counts
- **WAL health**: WAL file size, replay queue
- **Federation status**: connected peers, sync lag
- **Storage breakdown**: chunk count, manifest size, disk usage
- **Annotation count**: per-work annotation counts for data integrity
- **Checkpoint history**: recent checkpoint durations and success/fail

### Phase 3: Management actions
- **Force checkpoint**: trigger immediate checkpoint from UI
- **Block/unblock IP**: manage rate limiter from UI
- **View/rotate keys**: show key history, trigger rotation
- **Reload from backup**: show backup history, trigger restore
- **Server config**: view runtime configuration
- **Work management**: list all works with edit/delete capabilities

### Phase 4: Trending and alerting
- **Time-series graphs**: operations/sec, sessions over time, checkpoint duration
- **Threshold alerts**: configurable alerts via email/webhook
- **Data integrity checks**: verify all chunks, detect orphans
- **Performance profiling**: request latency, slow queries
- **Capacity planning**: growth trends, projected storage needs

## Data Sources

| Source | Endpoint | What it provides |
|---|---|---|
| Health | `GET /health` | Status, counts, checkpoint time |
| Server info | `GET /.well-known/xudanu-server.json` | Server name, address, protocol version |
| Security log | Chained log files | Tamper-evident audit trail |
| Session audit | `transport/audit` | Connection events |
| Rate limiter | In-memory | Blocked IPs, notification counts |

## Missing Critical Requirements

1. **Data integrity monitoring**: no automated check that all chunks are readable
   and match their hashes. A background verification job would detect corruption
   early.

2. **Backup verification**: backups exist (dual manifest slots) but there's no
   automated restore-test. A periodic test-restore would catch silent failures.

3. **Memory monitoring**: the `/health` endpoint doesn't report memory usage.
   For large docuverses, memory pressure could cause slowdowns before any
   visible error.

4. **Connection quality metrics**: no tracking of WebSocket disconnect rates,
   reconnection frequency, or average latency. These would reveal network or
   server performance issues.

5. **Disk space monitoring**: no disk space reporting. A full disk would cause
   checkpoint failures with no early warning.
