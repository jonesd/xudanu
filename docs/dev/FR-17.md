# FR-17: Storage Architecture — Gold vs Xudanu Trade-offs

> Concrete storage cost analysis and design decision record for the
> snapshot-based (Xudanu) vs enfilade/deep-versioning (Gold) trade-off.

## Executive Summary

Xudanu uses **snapshot-based revisions** with BLAKE3 content-addressed chunks.
Gold uses **enfilade-based deep versioning** with structurally shared subtrees.
For the common case (current version, collaborative editing), Xudanu is
**10-20× cheaper on disk**. Gold's structural sharing pays off only after
**~80-90 revisions** for small documents, or **~30-50 revisions** for large
documents.

## Storage Model Comparison

### Xudanu: Snapshot Chunks

```
Document (10 KB text)
├── Edition
│   ├── EntryChunk × N (256 entries each, postcard-serialized)
│   │   └── (position, RangeElement) pairs
│   ├── Root chunk (hash pointers + metadata)
│   └── Provenance vectors
├── Manifest WorkEntry (~200 bytes, hash pointers only)
└── BLAKE3 content-addressed → free dedup for identical chunks
```

- **1 byte format tag** per chunk (format byte + postcard payload)
- **~5 bytes per entry on disk** (position varint + tag + string)
- **Batching** (`from_text_batched`) groups by line: ~20 entries for 10 KB
- **CRDT is transient**: session_bases, awareness — in-memory only, not persisted
- **WAL is transient**: truncated on checkpoint (~80-150 bytes per operation while live)

### Gold: Enfilade Flocks

```
Document (10 KB text)
├── Snarfs (fixed-size disk blocks)
│   └── Flocks (persisted objects)
│       ├── Leaf loaves (content + OPart header + crumbs + region)
│       ├── Inner/Split loaves (tree structure, child pointers)
│       └── History canopy crumbs (HUpperCrum per versioned node)
├── Map cells (8 bytes per flock)
└── SnarfHeaders (integrity hash arrays per block)
```

- **8 bytes map cell** per flock (overhead before any content)
- **200-300 bytes structural overhead** per loaf node (OPart + hash + crumbs)
- **Copy-on-write versioning**: edit creates ~log(n) new path loaves, shares rest
- **History canopy**: HUpperCrum tree tracks which loaves belong to which version

## Concrete Storage Estimates

### Small text (1 KB, ~1 paragraph)

| | 1 version | 10 versions | 100 versions |
|---|---|---|---|
| Raw text | 1 KB | 1 KB | 1 KB |
| Xudanu (batched) | ~2 KB | ~20 KB | ~200 KB |
| Xudanu (per-char) | ~6 KB | ~60 KB | ~600 KB |
| Gold | ~80-135 KB | ~180 KB | ~490-540 KB |

### Medium document (10 KB, ~5 pages)

| | 1 version | 10 versions | 100 versions |
|---|---|---|---|
| Raw text | 10 KB | 10 KB | 10 KB |
| Xudanu (batched) | ~12 KB | ~120 KB | ~1.2 MB |
| Gold | ~200-400 KB | ~350-600 KB | ~1.5-2.5 MB |

### Large document (100 KB, ~50 pages)

| | 1 version | 10 versions | 100 versions |
|---|---|---|---|
| Raw text | 100 KB | 100 KB | 100 KB |
| Xudanu (batched) | ~110 KB | ~1.1 MB | ~11 MB |
| Gold | ~500 KB-1 MB | ~700 KB-1.5 MB | ~2-4 MB |

### Compound document (10 KB text + 5 transclusions + 20 links + 15 annotations)

| Component | Xudanu | Gold |
|---|---|---|
| Text content | ~12 KB | ~200-400 KB |
| 5 transclusion elements | ~500 bytes | ~1-2.5 KB |
| 20 typed links | ~3 KB | ~10-20 KB |
| 15 annotations | ~2 KB | ~8-15 KB |
| Provenance metadata | ~1 KB | ~5-10 KB |
| **Total** | **~18 KB** | **~230-450 KB** |

## Crossover Analysis

Gold's structural sharing becomes cheaper than Xudanu's full snapshots at:

| Document size | Crossover point |
|---|---|
| 1 KB (small) | ~80-90 revisions |
| 10 KB (medium) | ~60-70 revisions |
| 100 KB (large) | ~30-50 revisions |

**Why:** Larger documents have deeper enfilade trees (more shared subtrees),
so each revision writes fewer new nodes proportionally. Xudanu writes a
full snapshot every time regardless.

## CRDT vs Lock-Based Versioning

| Aspect | Xudanu CRDT | Gold locks |
|---|---|---|
| Concurrent editing | Multiple writers, three-way merge | One writer at a time (grab/release) |
| Memory cost | ~2-6 KB per active session (transient) | Minimal (lock state only) |
| Persisted cost | Zero — merged result is one revision | Zero — edit modifies enfilade directly |
| Edit history | Not kept (debounced, final result only) | Every edit is a new version in the tree |
| Conflict handling | Three-way merge with LWW (silent) | No conflicts possible (serialized) |
| Real-time collaboration | Yes (CRDT delta sync) | No |

## Xudanu's Advantages

1. **10-20× smaller for current version**: No per-flock map cells, no structural
   node overhead, no history canopy. A 10 KB document costs ~12 KB vs ~200-400 KB.

2. **Free deduplication**: BLAKE3 content addressing means identical chunks
   collide automatically. Two works with identical text share the same chunk.

3. **No operation log bloat**: CRDT merges are debounced and written as one
   snapshot revision. No permanent edit history accumulates.

4. **Simpler storage layer**: Chunk store + manifest + WAL. No snarf/flock/map-cell
   machinery. No integrity hash arrays per block.

5. **Real-time collaboration**: CRDT supports concurrent editing. Gold requires
   serialization (one writer at a time).

6. **Efficient for the common case**: Most collaborative documents need the current
   version, not 100 historical revisions. Xudanu optimizes for this.

## Xudanu's Gaps (Gold's Advantages)

1. **No structural sharing between revisions**: Each `revise()` writes a full
   snapshot. A 1-character edit in a 10 KB document writes ~12 KB, not ~2.5 KB
   of path loaves.

2. **No efficient cross-version queries**: "What did this passage look like in
   revision 47?" requires loading the entire revision-47 edition. Gold walks
   the history canopy in O(log V).

3. **No per-position version history**: Gold tracks which positions changed
   across versions via the enfilade tree structure. Xudanu would need to load
   two full editions and diff them.

4. **Revision history grows linearly**: 1000 revisions × 12 KB = 12 MB.
   Gold's 1000 revisions with structural sharing might be ~3-5 MB because
   unchanged subtrees are shared.

5. **No copy-on-write**: Xudanu has no mechanism to share interior structure
   between editions. Two editions that differ by one paragraph are stored
   as two complete, independent edition chunk sets.

## Design Decision: Why Snapshot-Based

Xudanu chose snapshot-based revisions for these reasons:

1. **Simplicity**: Snapshot + manifest is dramatically simpler than enfilade
   + canopy + flock + snarf. Less code, fewer bugs, easier to reason about.

2. **CRDT compatibility**: CRDT merging produces a complete edition, not a
   delta through a version tree. Snapshots align naturally with CRDT output.

3. **Modern storage is cheap**: In 2024+, disk space is not the bottleneck.
   Developer time and code complexity are. The 10-20× storage overhead of
   snapshots is acceptable for most use cases.

4. **Content addressing provides natural dedup**: BLAKE3 hashing gives
   dedup for free at the chunk level (256 entries). For truly identical
   revisions, the chunks collide and zero bytes are written.

5. **Batching mitigates overhead**: `from_text_batched` groups text by line,
   reducing per-entry overhead from ~5 bytes to ~1 byte overhead per character.

## Future Improvement Options

### Option A: Delta-based revision storage (medium effort)

Store only the delta between consecutive revisions instead of full snapshots:

```
Revision 1: full edition (~12 KB)
Revision 2: delta from rev 1 (~500 bytes for a small edit)
Revision 3: delta from rev 2 (~200 bytes)
...
```

**Pros**: Dramatic reduction for many-revision documents.
**Cons**: Loading old revision requires replaying deltas. No random access.
**Effort**: 2-3 weeks. Would use `Mapping::from_delta_ops` (already built in FR-14).

### Option B: Chunk-level structural sharing (large effort)

Split editions into smaller chunks (per-paragraph instead of per-256-entries).
Unchanged paragraphs would collide across revisions:

```
Revision 1: chunk(paragraph_1), chunk(paragraph_2), chunk(paragraph_3)
Revision 2: chunk(paragraph_1), chunk(paragraph_2_modified), chunk(paragraph_3)
                                    ↑ only this chunk is new
```

**Pros**: Automatic structural sharing via content addressing. Unchanged
paragraphs share the same chunk across revisions. Closer to Gold's efficiency.
**Cons**: More chunks = more manifest entries. Needs chunk-level provenance.
**Effort**: 3-4 weeks. Would need `simple_regions()` to split text into paragraphs.

### Option C: Copy-on-write edition tree (very large effort)

Implement a Gold-style enfilade with structural sharing. This is essentially
rebuilding Gold's core data structure.

**Pros**: Full deep versioning. Most efficient for many-version documents.
**Cons**: Massive engineering effort. Breaks CRDT compatibility. Gold's
enfilade took decades to build.
**Effort**: 3-6 months minimum.

### Option D: Garbage-collect old revisions (small effort)

Keep only the last N revisions per work. Old revisions are deleted, keeping
storage proportional to document size × retention window.

**Pros**: Simple. Bounds storage growth.
**Cons**: Loses history.
**Effort**: 2-3 days. Add `max_revisions` per work, GC old `EditionChunkRef`.

## Recommendation

**Option A (delta-based)** is the best near-term improvement. It uses the
space algebra we already built (`Mapping::from_delta_ops`) to store only
what changed between revisions. Combined with **Option D (revision GC)**,
this would give:

- Current version: full snapshot (~12 KB for 10 KB doc)
- Last 50 revisions: deltas (~500 bytes average each = ~25 KB)
- Older revisions: garbage collected

Total: ~37 KB for a document with 50 accessible revisions — competitive
with Gold's ~350-600 KB for the same.

Long-term, **Option B (chunk-level sharing)** would bring structural
deduplication closer to Gold's efficiency without the complexity of
enfilades.

## Option B Detail: Chunk-Level Structural Sharing

### The Problem with Current Chunks

Editions are stored as EntryChunks of 256 entries each, with **absolute
positions** stored inside each entry. When text is edited:

1. The entry at the edit point changes
2. All entries after it shift position → different varint encodings
3. The 256-entry chunk gets a new BLAKE3 hash
4. All subsequent chunks also get new hashes (positions shifted)
5. Root chunk changes (all chunk hashes changed)

**Result: a 1-character edit invalidates every chunk from the edit point
onward. No sharing between revisions.**

### Proposed: Paragraph-Level Chunks

Split editions into independently-addressed paragraph chunks. Each chunk
is self-contained — no absolute positions inside:

```rust
struct Edition {
    chunks: Vec<ParagraphChunkRef>,
}

struct ParagraphChunkRef {
    content_hash: [u8; 32],   // BLAKE3 of paragraph content
    char_len: u32,             // for computing absolute positions
    provenance: Option<[u8;32]>,
}

struct ParagraphChunk {
    elements: Vec<RangeElement>,  // text, transclusions — NO positions
}
```

Positions computed at load time by walking the chunk list:
```rust
fn absolute_position(chunks: &[ParagraphChunkRef], chunk_idx: usize, offset: usize) -> i64 {
    chunks[..chunk_idx].iter().map(|c| c.char_len as i64).sum::<i64>() + offset as i64
}
```

### How Revisions Share Chunks

```
Revision 1: [hash_A, hash_B, hash_C, hash_D]
Revision 2: [hash_A, hash_B2, hash_C, hash_D]  ← only paragraph B changed
Revision 3: [hash_A, hash_B2, hash_C2, hash_D]  ← only C changed
```

On disk:
- `hash_A` — stored once, shared by all 3 revisions
- `hash_B` — only revision 1
- `hash_B2` — shared by revisions 2, 3
- `hash_C` — revisions 1, 2
- `hash_C2` — only revision 3
- `hash_D` — stored once, shared by all 3

BLAKE3 content addressing = automatic dedup. No explicit tracking needed.

### Cross-Work Sharing

Same paragraph in two works → same hash → stored once:
```
Work Alpha: [hash_A, hash_B, hash_C]
Work Beta:  [hash_X, hash_B, hash_Y]  ← paragraph B shared on disk
```

### Span Migration: Two-Level Pipeline

With chunk-referenced editions, spans (links, annotations, transclusions)
store **chunk-relative positions** instead of absolute positions:

```rust
struct Span {
    chunk_idx: usize,       // which paragraph chunk
    offset_start: usize,    // offset within that chunk
    offset_end: usize,
}
```

Absolute position derived at read time. Migration happens in two phases:

**Phase 1: Chunk-level migration**

Build a Mapping that remaps old chunk indices to new chunk indices.
Spans in unchanged chunks need zero migration.

```
BEFORE: chunks = [A, B, C, D]
INSERT new paragraph E at index 2:
AFTER:  chunks = [A, B, E, C, D]

Chunk migration Mapping:
  idx 0 → 0 (unchanged)
  idx 1 → 1 (unchanged)
  idx 2 → 3 (shifted by +1, E inserted)
  idx 3 → 4 (shifted by +1)
```

Spans at chunk_idx 0 or 1: **no migration needed** — chunk exists in
both old and new edition with same hash.

Spans at chunk_idx 2+: chunk_idx shifts by +1. Apply via
`chunk_migration.of(old_idx)`.

**Phase 2: Text-level migration (only for spans in changed chunks)**

For spans whose chunk hash changed (paragraph was edited), apply existing
text-level migration using `map_span_through_delta`. This reuses the
space algebra's `Mapping::from_compound_delta_ops`.

Spans in unchanged chunks skip Phase 2 entirely — their offset is still
valid because the text hasn't changed.

**Concrete example — edit within paragraph 2:**

```
BEFORE:
Chunk 0: "First paragraph." (hash_A, len=16)
Chunk 1: "Second paragraph." (hash_B, len=17)
Chunk 2: "Third paragraph." (hash_C, len=16)

Link span at chunk 2, offset 0..5: "Third"

Insert 5 chars in chunk 1:
AFTER:
Chunk 0: hash_A (len=16)         ← UNCHANGED
Chunk 1: hash_B2 (len=22)        ← MODIFIED
Chunk 2: hash_C (len=16)         ← UNCHANGED hash
```

| Span | Phase 1 (chunk) | Phase 2 (text) | Result |
|---|---|---|---|
| Link at (2, 0..5) | chunk 2 hash_C unchanged → skip | skip | (2, 0..5) — zero migration |
| Annotation at (1, 5..10) | chunk 1 hash changed → needs Phase 2 | offset 5 > insert point → shift +5 | (1, 10..15) |
| Annotation at (0, 0..16) | chunk 0 unchanged → skip | skip | (0, 0..16) — zero migration |

**2 of 3 spans need zero migration.** Only the span in the edited
paragraph changes.

**Performance comparison:**

| Scenario | Current (absolute positions) | Chunk-referenced |
|---|---|---|
| 1 paragraph edited, 20 spans elsewhere | Migrate all 20 spans after edit point | Migrate only spans in 1 paragraph |
| Insert paragraph | Migrate all spans after insertion | Remap chunk_idx for spans after insertion; no offset migration |
| 100 spans in paragraph 5, edit in paragraph 2 | Migrate all 100 | Zero migration |

### What Changes

| Component | Current | Proposed |
|---|---|---|
| Edition internal | `Vec<(i64, RangeElement)>` | `Vec<ParagraphChunkRef>` |
| Chunk granularity | 256 entries | 1 paragraph per chunk |
| Position storage | Absolute (in each entry) | Computed (sum of chunk lengths) |
| Revision sharing | None (full snapshot) | Automatic (BLAKE3 dedup) |
| Cross-work sharing | None | Automatic (same text = same hash) |
| Span storage | Absolute positions | (chunk_idx, offset) pairs |
| Span migration | All spans after edit point | Only spans in changed chunks |

### What Doesn't Change

- Chunk store (still BLAKE3 content-addressed)
- Manifest (still stores WorkChunkRef per work)
- CRDT (merges editions; just merges chunk-reference lists)
- Space algebra (all operations still applicable)
- Comparison tool (delta + simple_regions already available)

### Effort: 3-4 weeks

High risk — touches the entire data layer.

### When to Implement

- When users create works with 100+ revisions
- When cross-work content sharing is important
- When storage growth becomes a user-visible problem
- NOT NOW — user-facing features are higher priority

## Decision: Wait

Current snapshot approach works. The space algebra supports the future
refactor. The design is saved. Priority goes to:

1. Perspective View Phase 1.5 (1 week, low risk)
2. Compound Builder Phase 2 (1 week, low risk)
3. Copy-detection / FR-10 (3-5 days, low risk)
4. Admin Dashboard Phase 2 (1 week, low risk)

If storage pressure arises before the full refactor, implement Option A
(delta-based revisions, ~2-3 weeks) as a cheaper intermediate step using
the `Mapping::from_compound_delta_ops` algebra already built in FR-14.
