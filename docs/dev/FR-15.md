# FR-15: Connect Space Algebra to Codebase

> Practical plan for bridging the trait-based `crate::space` module with the
> concrete `edition::{XnRegion, Mapping}` types used throughout the live system.

## The Problem

Two parallel implementations exist:

1. **`crate::space::*`** — generic, trait-based, well-tested
   - `Space`, `Position`, `Region`, `Dsp`, `OrderSpec` traits
   - Integer, Real, Sequence (tumbler), Cross (2D/ND), Filter spaces
   - ~1600 tests in `phase3_tests.rs`
   - **Never imported outside `src/space/`**

2. **`edition::{XnRegion, Mapping}`** — concrete, i64-only, used everywhere
   - `XnRegion` — transition-list region (now has delta, simple_regions)
   - `Mapping` — piecewise constant displacement (now has transformed_by, minus, compose_with, canonical combine)
   - Used by server, persist, edition, compound, three_way, backfollow
   - **2386 tests**

## Why They're Disconnected

The space module was built as a "reference implementation" of Gold's algebra.
It faithfully mirrors the Smalltalk class hierarchy. But the live system was
built pragmatically with concrete types — and it works. The two were never
bridged because:

1. **Different type signatures** — space traits use associated types; edition uses raw `i64`
2. **Different module boundaries** — `XnRegion` is in `edition/`, not `space/`
3. **No forcing function** — the live system works without the traits

## The Pragmatic Bridge

Rather than a big-bang refactor, we bridge incrementally:

### Approach: Adapter traits on concrete types

Make `XnRegion` and `Mapping` implement the space traits directly. They already
have all the methods — the traits just need wrapper implementations.

```rust
// New file: edition/space_bridge.rs
use crate::space::traits::{Region, Position, Dsp};

// Thin wrapper — XnRegion already has i64 positions
pub struct IntPos(pub i64);

impl Position for IntPos {
    type Region = XnRegion;
    fn as_region(&self) -> XnRegion {
        XnRegion::interval(self.0, self.0 + 1)
    }
}

impl Region for XnRegion {
    type Position = IntPos;
    // ... delegate to existing methods
}
```

This gives us:
- All space trait operations on `XnRegion` for free
- Generic algorithms that work over any `Region` can use `XnRegion`
- No changes to callers — purely additive
- The `space::integer::IntegerRegion` wrapper becomes unnecessary

### What this enables

1. **Generic region algorithms** — write an algorithm once against `Region` trait, works for integers, tumblers, cross-spaces
2. **Tumbler-based addressing** — `SequenceSpace` positions for cross-server content addressing
3. **Cross-space document maps** — `CrossSpaceN` for multi-dimensional document metadata
4. **Real filter queries** — `FilterSpace` with actual region matching for link queries
5. **Polymorphic comparison** — same diff algorithm works for any position space

## Implementation Phases

### Phase 1: Adapter on XnRegion (small, 1 day)

Add trait implementations for `XnRegion` and `i64`-based positions.

1. Create `edition/space_bridge.rs` with:
   - `impl Region for XnRegion` (delegates to existing methods + delta)
   - `impl Position for I64Pos` (thin wrapper)
   - `impl Dsp for I64Dsp` (thin wrapper over i64 offset)
   - Zero-cost — all methods already exist

2. Add tests proving trait operations match concrete operations:
   - `Region::delta` on XnRegion gives same result as `XnRegion::delta`
   - `Region::intersect` matches `XnRegion::intersect`
   - etc.

3. Verify the `space::integer::IntegerRegion` wrapper produces identical results

### Phase 2: Adapter on Mapping (small, 1 day)

Add trait implementations for `Mapping`:

1. `impl MappingSpace for Mapping` (if we add this trait)
2. Or: make `Mapping` satisfy the same algebraic laws as `space::mapping::SimpleMapping`
3. Add trait for `Mapping::transformed_by`, `compose_with`, `minus` at the trait level

### Phase 3: Delete IntegerRegion wrapper (medium, 2 days)

Once `XnRegion` implements `Region` directly:
1. `space::integer::IntegerRegion` becomes redundant
2. Update `phase3_tests.rs` to test `XnRegion` directly via the trait
3. Remove `IntegerRegion` or keep as deprecated alias
4. The space module becomes: traits + Real/Sequence/Cross/Filter (non-integer implementations)

### Phase 4: Use SequenceSpace for tumblers (large, future)

The biggest win from the space module:
1. Cross-server addresses currently use string-based tumblers (`"alice.com".5.3.10.7`)
2. `SequenceSpace` provides the proper algebraic representation
3. Sequence regions support prefix queries (`"all content under alice.com.5.*"`)
4. Sequence displacements support address migration

This is a significant refactor of the addressing system — separate FR.

### Phase 5: CrossSpace for document metadata (future)

`CrossSpaceN` enables multi-dimensional document maps:
1. (work_id, char_position) → Cross2<IntegerSpace, IntegerSpace>
2. (server_id, work_id, position) → Cross3<Sequence, Integer, Integer>
3. Enables spatial queries: "find all content in the rectangle [work_a..work_b] × [pos_10..pos_50]"

## Difficulty Assessment

| Phase | Effort | Risk | Value |
|---|---|---|---|
| 1: XnRegion adapter | Small | None — purely additive | Trait polymorphism |
| 2: Mapping adapter | Small | None | Trait polymorphism |
| 3: Delete wrapper | Medium | Low — tests catch regressions | Simplicity |
| 4: Tumbler addressing | Large | Medium — changes wire protocol | Cross-server correctness |
| 5: CrossSpace queries | Large | Low — new feature | Spatial document queries |

## Other Problems Fixed (this session)

1. **XnRegion fields now `pub(crate)`** — allows canonicalize and other algorithms to inspect internals
2. **`intervals()` handles unbounded regions** — `above(n)` and `full()` now return correct trailing intervals
3. **`simple_regions()` delegates to `intervals()`** — no code duplication
4. **`from_compound_delta_ops()`** — parallel to `from_delta_ops` for the `compound::DeltaOp` type
5. **`Mapping::of()` fixed** — missing `None` return and closing braces after edit

## What We Should NOT Do

- **Replace XnRegion with IntegerRegion everywhere** — massive refactor, no benefit
- **Rewrite server.rs to use trait objects** — performance regression, no benefit
- **Make all positions generic `P: Position`** — adds complexity where i64 is sufficient
- **Remove the space module** — it's a correct reference implementation and enables future features

## Recommendation

Do Phase 1-2 (adapters) now. They're small, safe, and enable trait-based polymorphism
without touching any callers. Defer Phase 3-5 until there's a concrete need (tumbler
addressing, spatial queries).
