What the network is

Xudanu is a transclusion-native hypertext system: documents quote, link, and build on each other by reference, with every origin preserved. A server is a complete, sovereign instance — its own corpus, its own users, its own rules. The network is what happens between sovereign servers:

  • Cross-server links — connect a passage on your server to a passage on another, bidirectionally. The other server is notified and its author sees the connection.
  • Transclusion — quote another server's text live, by address. If the source updates, your quotation points at the same spans; the content hash is verified on every fetch.
  • Global addressing — every passage has a network-wide name, a tumbler: "your.server.example".5.3.10.7 — your identity, the work, the span.
Sovereign servers, connected by verified reference — no central authority, no global index required.
The design principle: being able to READ the network is free; governing it is scarce. Joining the content network asks nothing of you and grants your users the whole docuverse to cite. Joint custody (shared stewardship) is a separate, opt-in commitment — see below.

Quick start: run a node

1

Get a server running

Grab a release binary or use Docker (published ports on 127.0.0.1 here — put a TLS terminator or a reverse proxy in front for production):

docker run -d --name xudanu \
  -p 8080:8080 \
  -v xudanu-data:/data \
  xudanu/server run 0.0.0.0:8080 /data \
    --server-name "Alice's server" \
    --public-address alice.example.com \
    --edit-policy public-sandbox
2

Declare your public address

--public-address is important: it becomes your network identity — the prefix of every tumbler your server mints, and the name other servers verify your signatures against. Use HTTPS in production (--public-address https://alice.example.com plus --tls-cert/--tls-key or a terminating proxy): cross-server exchanges verify content by hash and signature, but plaintext HTTP between servers can be observed and tampered with in transit (tampering is detected; privacy needs TLS).

3

Check your identity document

Your server automatically publishes its identity at /.well-known/xudanu-server.json — name, public address, Ed25519 verifying key, tumbler identity, content API. Other servers use this to verify that links and notifications claiming to be from you really are:

curl https://alice.example.com/.well-known/xudanu-server.json
4

Protect your admin surface

Admin login is fail-closed: without XUDANU_ADMIN_PASSPHRASE set, admin cannot be logged into at all — not "default password," but "no password works." Set yours via environment variable, never on the command line (visible in ps).

Connecting to other servers

Connections are deliberate, not automatic. To work with another server:

StepHow
Add them to your server directoryServer settings → Directory: add bob.example.com. Your server fetches their .well-known and records their verifying key.
Link acrossIn the editor, select text → link → remote server. Paste or pick the remote passage; a tumbler-addressed link is created.
TranscludeCopy a passage on a remote server, paste into your document — the paste offer includes “transclude instead of copying.” Quotation by reference, hash-verified on every fetch.
See who cites youBacklink notifications arrive signed; your Connections panel shows cross-server citations with their origin server.
What a receiving server verifies today: every backlink notification is checked twice — the Ed25519 signature over the body, and that the claimed key matches the one the origin publishes in its .well-known. Unsigned notifications are rejected. Forged "from alice.example.com" claims require Alice's private key.

Trust & security baseline

What every node on the network can assume about every other node:

GuaranteeMechanism
Content is what it claimsBLAKE3 content hashes on every cross-server fetch; mismatch = rejection
Notifications are authenticSigned backlinks + .well-known key binding (no spoofed origins)
Private works stay privateCross-server APIs serve public-club works only; private works are invisible (404-shaped)
One bad server can't flood youPer-IP and per-server rate limits; bounded backlink storage (200/work, 10k total, oldest evicted)
Slow peers can't stall youBounded timeouts on every cross-server call — a blackholed server costs you seconds, never minutes
Everything is auditableTamper-evident chained security log on every server
Outbound fetches can't be weaponizedSSRF guard: servers refuse to fetch private/internal addresses (test setups opt in explicitly)

Shared stewardship (optional) opt-in

Some corpora deserve joint custody: no single operator can un-publish, suspend, or rotate keys unilaterally. That's the federation mesh — Byzantine fault tolerant governance over the same servers. It is entirely optional: content federation (everything above) requires no membership.

When you want it

  • A shared corpus owned by several organizations
  • "Hit by a bus" continuity — the corpus survives any one operator
  • Adversarial settings where unilateral destructive power is unacceptable

How it works

Four servers is the minimum (BFT needs 3f+1). Membership is genesis-pinned: the founding operators exchange verifying keys (each prints theirs at boot: docker logs <node> | grep "verifying key"), write a shared pinned-members.json, and every node starts with --pin-members /data/pinned-members.json plus --peer entries for the others. From then on:

  • Decisions (un-publish, member suspension, key rotation) need quorum — 3 of 4
  • A member that signs conflicting votes (equivocation) is detected and suspended automatically, with an audit event
  • Validator keys have sequence-bounded epochs; expiry is visible in /health before it bites
  • Everything users do stays exactly the same — governance never touches the editing hot path
The key-custody rule: four nodes run by one operator give you fault tolerance against machine failure — not against that operator being compromised. Shared stewardship's real security arrives when the keys live with different people. Trade keys in person if you can; certainly not over the same channel the servers talk on.

Operating a node

Monitor /health

The health endpoint carries a federation section that makes liveness visible from outside:

{
  "federation": {
    "peers":              { "bob.example.com": { "connected": true, ... } },
    "peer_connected_count": 1,
    "governance":         { "current_view": 0, "last_sealed_seq": null, ... },
    "cross_server_notify": { "sent": 12, "accepted": 11, "failed": 1, "last_error": null }
  }
}

Watch three things: peer_connected_count (a half-down mesh looks identical to no mesh without it), cross_server_notify.failed climbing (delivery problems), and governance.last_sealed_seq stuck while rounds are expected.

Backups & keys

  • scripts/backup-offsite.sh — data-dir backup (works chunks are content-addressed; restores are clean)
  • Your Ed25519 keypair IS your identity. Losing it means a new identity (your old tumblers point at the old key); back it up. Key rotation with proof continuity is built in (/.well-known publishes rotation proofs)
  • Storage: content-addressed chunks dedupe naturally; the 4-node test bed runs ~13 MiB/node idle

Capacity notes

Content federation scales wide — pairwise, verified, stateless; hundreds of servers interlink comfortably. Governance mesh: plan for 4–20 nodes (PBFT's classic envelope). A single server carries hundreds of concurrent editors (CRDT merging is local-first).

What's coming

  • Network search (FR-91a): search the whole network from your editor — your server fans queries out across your trusted directory, routed by bloom filters so most peers are never asked, with signed, attributable results.
Try it locally: the repo ships a 4-node federation test bed — docker/docker-compose.yml — with a cross-server network test that exercises healthy delivery, down peers, blackholes, and restart persistence. If you're evaluating a mesh, start there.
