Federation Activation

How independent Xudanu servers connect, trust each other, and keep content in sync — and the wiring (FR-3) that turns the finished components into a running federation.

What a federation is

A Xudanu federation is a set of independent server peers, each a full node (it serves the web UI, the client WebSocket /xudanu, and the peer WebSocket /federation). Peers connect to each other, replicate content (chunks verified by BLAKE3), maintain a shared membership via a web-of-trust of Ed25519 endorsements, and make cluster-wide decisions with PBFT consensus. Users connect to any peer's web UI; the peers federate behind the scenes.

Current state: every building block (CRDTs, PBFT core, web-of-trust crypto, BLAKE3 replication, the mutual handshake, all inbound handlers) is implemented and merged (phases 14–19). What's missing is the activation layer — the runtime wiring that makes peers actually dial out, bootstrap, register keys, sync, and broadcast. That is FR-3.

Three full-node peers on a private network. Users hit any peer's web UI; peers replicate content and membership over /federation.

The activation layer (FR-3)

Five pieces of runtime wiring turn the finished components into a live federation. Today the server is passive — it accepts inbound /federation sockets but never reaches out. Each item below is the missing "active" half.

1. Outbound dialer — the hard blocker

On startup, a task per --peer address dials ws://peer/federation, performs the existing mutual handshake as the client side, and holds the encrypted channel in a pool (with reconnect/backoff). All the inbound frame handlers already exist — this is the missing initiator that lets a peer send frames to others.

2. Startup bootstrap

When federation is enabled, call membership_bootstrap_init() at startup so the node has a self-endorsed membership entry (it can act as a founder or a peer others can validate). Today this is only called from a unit test.

3. Peer-key registration — fixes the reject-all trap

A way to register trusted peer verifying keys (--trusted-peer-key <hex> or a file) that calls federation_register_peer_key. Without it, is_peer_known rejects every connection when federation is enabled — a self-DoS. This is the smallest fix and unblocks everything.

4. Periodic sync / heartbeat loop

On each live outbound channel, periodically send Heartbeat (liveness) plus SyncPull/SyncPush (content), MembershipSyncPush, StateSyncPush, EndorsementSyncPush. All the receiving handlers already exist — this is pure orchestration that turns "connected" into "converged."

5. PBFT broadcast

When an admin proposes governance, the leader broadcasts GovernancePrePrepare to peers; replicas relay Prepare/Commit votes to each other and broadcast Sealed. Today proposals die on the proposing node — votes only flow inbound.

How a donated machine joins

Identity is the server's existing Ed25519 keypair (data/server.key); trust is a web-of-trust of signed endorsements (phase-19a, already built). A donated host proves who it is by its key, and gets vouched for by an existing member.

A donated host bootstraps, dials a founder, completes the mutual handshake, has its key registered, then joins with an endorsement — membership converges cluster-wide.
No central authority. Trust is peer-signed and auditable; a compromised donor can be ejected via signed retraction or a PBFT Expel transaction. Each donor bears their own machine, so cost stays distributed — there is no expensive central fleet.

Testing it: Docker test bed

The docker-compose.yml runs three full-node peers on a private bridge network (host ports 8081/8082/8083), each with --peer pointing at the other two. On a 32 GB machine this is trivial for small/fresh data dirs — you could run 5–10+ peers; 3–4 is the sweet spot for exercising PBFT quorum and membership.

docker compose up --build
# then browse:
open http://localhost:8081   # peer A
open http://localhost:8082   # peer B
open http://localhost:8083   # peer C
Reminder: until FR-3 (items 1–5 above) is implemented, these containers run as standalone servers that do not yet federate — the compose is the test harness, ready and waiting for the activation wiring.

Sequencing

1
Peer-key registration + bootstrap (3 + 2) — smallest; fixes the reject-all trap so anything can connect.
2
Outbound dialer (1) — the hard blocker; without it nothing is active.
3
Sync / heartbeat loop (4) — turns a connection into convergence.
4
Donated-host join + PBFT broadcast (5, join flow) — cluster-wide trust and decisions.
