Compound Documents

How live transclusion works in Xudanu: documents assembled from live pieces of other documents, not copies.

1. The Core Concept

A compound document is a document whose content is assembled from live pieces of other documents. When a source document changes, every compound document that references it automatically reflects the change. This is Ted Nelson's original vision for transclusion: the same content can appear in multiple places simultaneously, always in sync, without duplication.

Figure 1: A compound document references live content from source works. Editing a source updates all compounds that reference it.

2. The Three Stores

Every work in Xudanu has up to three separate data stores that can hold text content. Understanding how they interact is the key to understanding the system:

Figure 2: Three stores coexist inside each work. They overlap but serve different purposes.

Why it's confusing: Placing a transclusion writes all three stores simultaneously. The O-tree gets a text copy, the compound edition gets a span reference, and the link system gets an attribution record. They can drift apart if edited independently.

3. Mechanism 1: The O-Tree (Static Text)

This is the primary content store. When you type in the editor, you're modifying the O-tree. It's a CRDT — conflict-free, supports concurrent editing, and persists as numbered revisions. 

Edition {
    orgl_root: OrglRoot,      // the ordered tree (o-tree)
    endorsements: [...],      // who has vouched for this
    // entries: [(position, RangeElement)] — text characters at positions
}

// What you see in the editor IS the O-tree text
editor.textContent === otree.get_text()

When text from another work is pasted into the O-tree, it becomes a copy. It does not update when the source changes. This is just like copying text in a normal editor.

4. Mechanism 2: Compound Editions (Live Spans)

A compound edition is an ordered list of elements, each either literal text or a live span reference: 

CompoundEdition {
    elements: [
        Text { content: "Introduction. " },
        Span  { span: CompoundSpan {
            source_work_id: 1006,   // which work to reference
            char_start: 0,          // character offset in source
            char_end: 46,           // end offset (exclusive)
        }},
        Text { content: " Conclusion." },
    ]
}

The span doesn't store text. It stores a pointer (work_id, char_start, char_end). When you resolve the compound, the system fetches current text from each source and assembles the result:

5. Mechanism 3: Transclusion Links (Attribution)

Links are the provenance and attribution layer. They record why a piece of text appeared in your document, who put it there, and the chain of derivation: 

HyperLink {
    link_id: 0x1A2B,
    origin: this_work,          // where the link lives
    destination: source_work,   // where the content came from
    origin_ref: HyperRef {      // the span in THIS work
        start_position: 42,
        end_position: 88,
        excerpt: "The quick brown fox",
    },
    link_types: [3, 7],         // typed links (quotation, paraphrase, etc.)
}
Key distinction: Compound spans answer: "What text should I show here?"
Links answer: "Where did this text come from and who vouches for it?"
A transclusion creates both, but they serve different purposes and can exist independently.

Figure 5: A single "place transclusion" action writes to all three stores simultaneously.

6. The Placement Flow

Here's exactly what happens when you place a transclusion today:

Step-by-step
// 1. Select text in source work
holdSelection(excerpt, sourceWorkId, charStart, charEnd)

// 2. Navigate to target compound work
//    TransclusionBadge appears with held excerpt

// 3. Place transclusion at cursor position
handlePlaceTransclusion(position):
    // A. Insert excerpt into O-tree (STATIC COPY)
    setText(text.slice(0, pos) + excerpt + text.slice(pos))

    // B. Record compound span (LIVE REFERENCE)
    compound.addSpan(text, pos, excerpt, sourceWorkId, charStart, charEnd)

    // C. Create attribution link (METADATA)
    transclusion.placeTransclusion(sourceWorkId, excerpt, charStart, charEnd)
The drift problem: If you later edit the O-tree text directly (delete the paragraph, add text around it), the O-tree text and the compound edition diverge. The compound panel lets you fix the compound edition, but the O-tree copy becomes stale. This is the core UX confusion.

8. The Design Tension

There are two possible architectures. Xudanu is currently straddling both:

Architecture A: Side-table (CURRENT)
Work B
+--------------------+ +------------------+
| O-Tree (primary)   | | Compound Edition |
| "Intro Hello End"  | | [Text,Span,Text] |
| (editable copy)    | | (live references)|
+--------+-----------+ +--------+---------+
         |                     |
    editing mode          reading mode
    shows this            shows resolved

Problem: two copies of content, can drift apart

Architecture B: Primary (FUTURE)
Work B (compound type)
+--------------------------------------+
| Compound Edition = THE document     |
| [Text, Span→A, Text, Span→B, Text] |
|                                      |
| Resolved text is the ONLY text       |
| No O-tree copy needed                |
+--------------------------------------+

Benefit: no drift — single source of truth

Architecture B would eliminate the drift problem entirely, but requires a new work type whose primary content IS the compound edition. The O-tree would only be used for non-compound works. This is the direction we're heading.

9. Incremental Composition

Compound editions can be edited element-by-element using three incremental operations. Each operation persists via WAL and takes effect immediately:

OperationOpcodeWhat it does
CompoundInsertElement 0x1D06 Insert a text literal or span reference at a given index
CompoundRemoveElement 0x1D07 Remove the element at a given index
CompoundMoveElement 0x1D08 Move an element from one position to another (reorder)

10. Use Cases: Simple to Visionary

Level 1 — Quotation Anthology

A document collecting excerpts from multiple source works. Each excerpt is a live span — if a source is corrected or updated, the anthology reflects it automatically.

CompoundEdition {
    Text { "Notable quotes:\n\n" },
    Span { src: Shakespeare, [120:145] },  // "To be or not to be..."
    Text { "\n\n — Hamlet\n\n" },
    Span { src: Tolstoy, [3000:3080] },    // "All happy families..."
    Text { "\n\n — Anna Karenina" },
}
Level 1 — Shared Boilerplate

Maintain a single "disclaimer" work. Every document that needs the boilerplate references it via a compound span. Update the source once, all documents update everywhere.

Level 2 — Collaborative Study Guide

A study guide assembling passages from a textbook (source) with interleaved commentary (literal text). When the textbook is revised, the passages update automatically.

Text { "Chapter 3 discusses recursion. Key passage:\n\n" },
Span { src: Textbook, [4500:4600] },     // textbook passage
Text { "\n\nAnalysis: The author's approach..." },
Span { src: Textbook, [4800:4900] },     // another passage
Text { "\n\nThis connects to..." }
Level 2 — Multilingual Parallel Text

Original text and translation shown side by side. Both are sources. Edits to either propagate to the parallel reading view.

Level 3 — Golden Thread / Deep Transclusion

A compound document references another compound document, which references another, creating a chain. Resolution follows the chain recursively (up to 32 levels). This is Nelson's "golden thread" — following content back through layers of derivation.

Doc C (compound) → spans in Doc B (compound) → spans in Doc A (source)

Resolving Doc C:
  1. Fetch Doc B's compound edition
  2. For each span in Doc B, resolve against Doc A
  3. Assemble final text from the entire chain
Level 3 — Versioned Anthology with Reordering

An editor reorders, adds, and removes excerpts using incremental compound ops (insert, remove, move) without affecting source works. All spans remain live throughout restructuring.

Vision — Nelson's Docuverse

In the full vision, everything is transclusion. No document copies content — every document is a compound of live references to a universal docuverse. Authors receive micropayments when their content is transcluded. Copyright becomes attribution tracking rather than access control.

Xudanu implements the technical foundation: content-addressed storage, live span references, recursive resolution, and per-element provenance. The economic and social layers are future work.
